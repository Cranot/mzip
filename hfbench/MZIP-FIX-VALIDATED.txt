=============================================

ROOT CAUSE -- TWO FAILURE MODES, MINIMAL REPRODUCER IS TWO BYTES
------------------------------------------------------------------
encode_num_extract (mzip.hpp:10376) parses each digit run with
    num = num * 10 + (data[i] - '0')
into a uint32_t, and the decoder re-emits the VALUE. Two things are therefore
unrepresentable, both measured with build/ne_probe:

  MODE 1 -- LEADING ZEROS DESTROYED
    "2" OK | "02" LOSSY | "007" LOSSY | "0" OK | "00" LOSSY | "x01y" LOSSY
    A zero-padded run decodes back shorter. Minimal reproducer: the two bytes "02"
    (encodes to 36 B, decodes to 1 B).
  MODE 2 -- UINT32 OVERFLOW
    "4294967295" OK | "4294967296" LOSSY | "99999999999" LOSSY
    Any value >= 2^32 wraps and decodes wrong.

Both are everywhere in real config data: zero-padded versions/dates/ids, and
nanosecond timestamps or token counts above 4.29e9.

SOURCE FIX (NOT YET APPLIED -- the guard below is what shipped)
----------------------------------------------------------------
detect_num_extract must refuse a digit run that (a) has a leading '0' and length
> 1, or (b) exceeds UINT32_MAX. Refusing to encode what cannot be reproduced is
the cure; the adoption guard is defence in depth.

REGRESSION TEST -- NOT YET WRITTEN, AND THE FIRST ATTEMPT WAS VACUOUS
-----------------------------------------------------------------------
The suite already has a `uRAW-BLOAT PATHOLOGY GUARDS` section with
no_uraw_bloat_bigint_unsigned_sql and no_uraw_bloat_repetitive_syslog, i.e. the
right home and idiom already exist (is_uraw_wholefile() + a ratio assert +
roundtrip). A third guard belongs there.
A first synthetic candidate (400 lines of JSON with "04"/"007"/>2^32 values,
25,615 B) was FALSIFIED AGAINST THE STOCK BUILD and did NOT reproduce -- stock
and patched both returned 167 B, because the input was so repetitive a template
encoder won at 153x before NUM_EXTRACT was ever considered. That test would have
passed on broken code and proved nothing. It was discarded rather than shipped.
A valid fixture must be >= ~16 KB, mid-entropy, and varied enough not to be
captured by an earlier detector. The real file's 16 KB prefix satisfies this and
is the recommended fixture.
Separately, a CODEC-level test over {"02","007","00","x01y","4294967296",
"99999999999"} fails on BOTH builds today and is the correct test to add
alongside the source fix.

TWO CORRECTIONS TO EARLIER CLAIMS IN THIS SESSION
---------------------------------------------------
- "ASan found a heap-buffer-overflow in encode_num_extract." WRONG, and the bug
  was MINE. bisect.cpp:44 computed `end - start - step` in size_t with
  step=4096 > end=475, underflowing to ~1.8e19, so the harness asked the encoder
  to read 18 exabytes. With the bounds fixed the same ASan build runs to
  completion, exit 0, no error. mzip is clean here.
- "87% of runtime is wasted; a free 8-55x speedup is available." WRONG. The
  bwt9 backstop is already memo-guarded (`if (!bwt9_memo_valid)`) and carries a
  deliberate comment on why a CAPPED result must not be cached. Its 0 hits mean
  it is a genuine trial that LOSES on HF data, not duplicated work, and the
  families owning that time are load-bearing elsewhere (ablation.md: GRID
  418,875 B, FILTER 645,475 B). A speed win must come from MZIP_FAMILY_MASK
  ablation measuring time-cost vs byte-win per family, not from deleting trials.
